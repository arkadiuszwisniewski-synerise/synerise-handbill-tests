Activate or redeem a promotion for this client

Picks a promotion from the results above and uses the client picked in the top bar. Activate POSTs to activate-for-client/{identifierType}/{identifierValue} (optional pointsToUse applies to cashback promotions). Redeem POSTs the promotion code to promotion/redeem (optional quantity = number of redeemed items) — the API accepts it only for ACTIVE promotions, so activate first or expect an error.

Promotion: get / create / update

get GETs /v4/promotions/promotion/{uuid|code}/{value} (GetPromotionDetailsAsBusinessProfile) — the promotion's workspace configuration, no profile context (the uuid/code show up in Fetch handbill, Create promotions and List matching results). ⤵ insert fetched copies the fetched promotion into the editor, trimmed to the writable fields (read-only ones like uuid, counters and timestamps would pollute the update) — null/empty values are dropped too, since omitted fields stay unchanged anyway and echoing them back trips validation (add a null back by hand to clear a field on purpose). update PUTs the editor's JSON to the promotion picked above — a partial update: only the fields you send change, but an explicit null overwrites the stored value. create POSTs the editor's JSON as a new promotion — remember to change code and headerName first when starting from a fetched promotion (code must be unique).

Brickworks output

preview record GETs the full schema from /brickworks/v1/schemas/{id} — and, when a record is picked, its values from …/records/{recordId} — then POSTs everything with the client picked in the top bar to /brickworks/v1/schemas/records/preview/by/{identifierType} (previewObject) — a dry run, no event. No record picked → the API renders from the schema's published data (SINGLETON schemas always render their record implicitly — values is only sent for other types). generate record POSTs to /brickworks/v1/schemas/{schemaId}/records/{recordId}/generate/by/{identifierType} (generateObjectForProfile) — generates from the latest published version of the record and emits the brickwork.generated event on the profile. Identifier mapping: clientId → id, customId → custom_identify.

Voucher pools

Vouchers

POSTs to /v4/vouchers/item (CreateAVoucher), count times. Placeholders in code: {rand5}, {date}, {serial}, {iso} — re-rolled per request; empty code is omitted. To hand the voucher to a profile, set clientId (profile ID) or clientUuid and status: ASSIGNED.

check voucher GETs /v4/vouchers/item/{searchKey}/{searchValue} (ViewVoucherDetailsBySearchKey) and shows the voucher's current status, assigned profile and dates. redeem voucher POSTs the same value to /v4/vouchers/item/redeem (RedeemAVoucher — requires by = code) and flips the status to REDEEMED. The value is prefilled with the first code from the last Create run.

vouchers for profile GETs /v4/vouchers/item/get-assigned-for-client/by-identifier — all vouchers assigned to the client picked in the top bar. Identifier mapping: clientId → id, customId → custom_identify.

batch redeem for profile POSTs a bare array (one item per code) to /v4/promotions/voucher/batch-redeem-for-profile (BatchRedeemVouchersForProfile, promotions service — redeems vouchers connected to promotions, not standalone pool codes). Partial failures come back as 207 with per-item errors. The documented options object is rejected by the live API, so it's not sent.

Add event/transaction to profile

type
params (optional — free-form event parameters)
transaction payload (JSON — client is injected from the top bar)

POSTs to /v4/events/custom (CustomEvent), count times, for the client picked in the top bar. action must be noun.verb (e.g. test.event); label is required by the API but not saved and can't be used in Analytics. Placeholders in label/eventSalt: {rand5}, {date}, {serial}, {iso} — re-rolled per request. params can be clicked together key by key (values are JSON-parsed when possible — 42, true, null, ["a"] — otherwise sent as strings) or pasted as one JSON object via the raw JSON toggle; switching modes converts the current input. Empty time → the API stamps the current time. Identifier mapping to the client object: clientId → id (integer), customId → customId. The API replies 202 Accepted — check the profile's activity log to see the event.

POSTs the payload to /v4/transactions (CreateATransaction), count times, with client injected from the top bar (clientId → id integer, customId → customId). Required: orderId, products (each needs name + finalUnitPrice), paymentInfo.method, revenue, value, source. All amounts must share one currency; revenue/value are not auto-calculated from products. Placeholders {rand5}, {date}, {serial}, {iso} work in any string value and re-roll per request, so orderId stays unique across repeats. Optional: recordedAt (ISO, no future times), eventSalt (same salt+recordedAt+client+orderId = overwrite), discountAmount (> 0 or omit), metadata. The API replies 202 Accepted and emits transaction.charge plus one product.buy per item.

Process basket / checkout (POS)

transaction JSON (string placeholders re-roll per request)

process basket POSTs the JSON to /v4/promotions/v2/sale/process-sale/{identifierType}/{identifierValue} (processSale) — evaluates the basket against the profile's promotions; it also accepts an optional promotionsToActivate array ({ "key": "uuid"|"code", "value": "…", "pointsToUse": 0 }). process checkout POSTs to /v4/promotions/sale/process-checkout/{identifierType}/{identifierValue} (processCheckout) — finalizes the transaction and additionally requires paymentsReport.paymentItems. The client comes from the top bar (mapping: customId → externalId). Placeholders {rand5}, {date}, {serial}, {iso} work in any string value — the templates use them for clientDateTime and globalTransactionId. Money fields (finalValue, prices) are strings; quantity takes 3 decimal places.

Batch overwrite (targetSegment)

POSTs { "data": [ … ] } to /v4/promotions/v2/promotion/batch (BatchImportPromotions). Matching is by code; it's a partial merge/upsert (async, 202), so each item sends only { code, targetType: "SEGMENT", targetSegment } — all other fields on the promotion are left untouched. (If a code doesn't exist yet, batch creates it.) After overwriting, re-run List matching below (or fetch for a client) to confirm the segment changed.

Handbill configuration

check GETs /v4/promotions/handbill/{handbillUuid} — the workspace configuration of the campaign, no profile context (and prefills the editor above if it's empty). ⤵ insert fetched copies the last fetched configuration into the editor (overwriting it), trimmed to the fields the PATCH accepts: channel, status, name, description, controlGroup, variants — the read-only rest (uuid, createdAt, …) would fail with a 422. update PATCHes the JSON above to the same endpoint — start from the fetched configuration and edit it, so no field gets nulled by an incomplete payload.
